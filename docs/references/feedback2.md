# 📖 คำอธิบาย Feedback ฉบับเข้าใจง่าย (สำหรับมือใหม่) และสรุปการแก้ไข

เอกสารนี้สรุปและแปลความหมายจากไฟล์ `feedback.md` ให้เป็นภาษาง่ายๆ เปรียบเทียบให้เห็นภาพชัดเจน พร้อมสรุปจุดที่ได้ดำเนินการแก้ไขในโค้ดและฐานข้อมูลเรียบร้อยแล้ว

## 🌟 1. จุดที่ผู้ตรวจชมว่าทำได้ดีมากแล้ว (จุดแข็งของโปรเจกต์)

- **แยกหน้าที่ไฟล์ชัดเจน (แยก Layer):**
  - แยกไฟล์ `routes` (เส้นทาง URL), `controllers` (สมองคิดงาน), `validators` (ตัวตรวจข้อมูล), และ `middlewares` (ยามเฝ้าประตู) ออกจากกันเป็นระเบียบ ไม่ปนกันมั่ว
- **ระบบล็อกอินปลอดภัยถูกหลัก:**
  - เก็บบัตรผ่าน (Token) ไว้ใน `HttpOnly Cookie` (ปลอดภัยกว่าการเก็บใน `localStorage` เพราะ JavaScript ฝั่งหน้าเว็บแอบดึงไปไม่ได้)
  - เข้ารหัสผ่านด้วย `bcrypt` (ไม่ได้เก็บรหัสผ่านจริงเป็นตัวอักษรตรงๆ ลงฐานข้อมูล)
  - เวลาล็อกอินผิด ระบบตอบกลับว่า *"Username หรือรหัสผ่านไม่ถูกต้อง"* โดยไม่หลุดบอกแฮกเกอร์ว่าผิดที่ช่อง Username หรือช่อง Password
- **กัน SQL Injection และดักข้อมูลขาเข้า:**
  - ใช้ `Zod` ตรวจสอบความถูกต้องของข้อมูลที่ส่งมาจากฟอร์ม ร่วมกับ `role.middleware.ts` กั้นสิทธิ์ผู้ใช้งาน
  - ใช้ `Drizzle ORM` คุยกับฐานข้อมูล ช่วยป้องกันการแฮกแบบ SQL Injection อัตโนมัติ
- **มีตัวกั้นก่อนปิดงานซ่อม (Validation Guard):**
  - บังคับว่าต้องเลือกบริการที่ซ่อมจริง (`service_id`) ก่อน จึงจะกดเปลี่ยนสถานะเป็น *"ซ่อมเสร็จแล้ว (completed)"* ได้
- **README ละเอียด:**
  - มีเอกสารอธิบายโครงสร้างโปรเจกต์และวิธีใช้งานชัดเจน

## 🛠️ 2. รายการที่ต้องแก้ 7 ข้อหลัก (เรียงจากสำคัญมาก → น้อย)

### ข้อ 1: `JWT secret มี fallback ฝังในโค้ดและอยู่ใน README → ถ้าไม่มี env ให้ server ไม่ยอมสตาร์ท`
- **แปลภาษาง่ายๆ:**
  - `JWT_SECRET` เปรียบเหมือน **"แม่พิมพ์ปั๊มบัตรผ่านแอดมิน"**
  - เดิมทีในโค้ดเขียนดักไว้ว่า `process.env.JWT_SECRET || 'repair_service_secret_key_2026_change_in_production'` แปลว่า *"ถ้าลืมตั้งค่าในไฟล์ `.env` ให้แอบใช้รหัสสำรองที่พิมพ์ฝังไว้ในโค้ดแทน"* แถมรหัสสำรองนี้ดันโชว์อยู่ในหน้า `README.md` ด้วย!
  - ถ้าคนนอกมาอ่านโค้ดหรืออ่าน `README.md` เขาก็รู้รหัสแม่พิมพ์นี้ แล้วนำไปสร้างบัตรผ่านปลอมตัวเป็น Admin เข้ามายึดระบบได้ทันที
- **วิธีแก้ไขที่ทำแล้ว:**
  - สร้างไฟล์ `backend/src/config/env.ts` เพื่อบังคับว่า **ต้องตั้งค่า `JWT_SECRET` ใน `.env` เท่านั้น** หากไม่มีค่านี้ เซิร์ฟเวอร์จะแจ้ง Error และ **ไม่ยอมเปิดทำงานทันที (`process.exit(1)`)**
  - ลบรหัสสำรองออกจาก `auth.middleware.ts`, `auth.controller.ts`, `.env.example` และ `README.md`

### ข้อ 2: `CORS เปิดทุก origin พร้อม credentials → ใช้ whitelist จาก CLIENT_URL`
- **แปลภาษาง่ายๆ:**
  - `CORS` เปรียบเหมือน **"ยามเฝ้าประตูหลังบ้าน"** ที่คอยตรวจว่าเว็บไซต์หน้าบ้าน (Frontend) จากชื่อโดเมนไหนบ้างที่ได้รับอนุญาตให้ส่งคำสั่งพร้อมแนบ Cookie (`credentials: true`) เข้ามาหา Backend ของเราได้
  - เดิมตั้งค่าเป็น `origin: true` แปลว่า *"เปิดรับทุกเว็บไซต์บนโลกใบนี้เลย"* ซึ่งอันตรายมาก เพราะถ้าแอดมินเผลอเปิดเว็บแปลกปลอม เว็บนั้นอาจแอบส่งคำสั่งมาที่ Backend ของเราโดยใช้ Cookie แอดมินที่ค้างอยู่ในเบราว์เซอร์ได้
- **วิธีแก้ไขที่ทำแล้ว:**
  - แก้ใน `backend/src/index.ts` และ `backend/src/config/env.ts` ให้สร้าง **บัญชีรายชื่อเว็บที่อนุญาต (Whitelist)** จากตัวแปร `CLIENT_URL` ใน `.env` เท่านั้น (รองรับการใส่หลายโดเมนคั่นด้วยลูกน้ำ `,` และรองรับโดเมนของ Vercel อัตโนมัติ) ถ้าเว็บไหนไม่อยู่ในรายชื่อจะถูกบล็อกทันที

### ข้อ 3: `รายรับดึงราคาปัจจุบันของ service → แก้ราคาหรือลบบริการแล้วยอดย้อนหลังเพี้ยน ต้องเก็บ final_price กับ completed_at ตอนปิดงาน`
- **แปลภาษาง่ายๆ:**
  - ลองนึกภาพร้านซ่อมคอมพิวเตอร์: เดือนมกราคม ซ่อมจอให้ลูกค้าไปในราคา **1,500 บาท**
  - พอเดือนกุมภาพันธ์ ร้านปรับราคาบริการเปลี่ยนจอขึ้นเป็น **2,000 บาท** (หรือเผลอลบบริการนั้นทิ้ง)
  - ระบบเดิมไม่ได้จดราคาตอนที่ซ่อมเสร็จไว้ในใบงาน (`inbox_messages`) แต่ใช้วิธีไปดึงราคาปัจจุบันจากตาราง `services` มาบวกเลขใหม่ทุกครั้ง! พอแก้ราคาเป็น 2,000 บาท ยอดขายย้อนหลังของเดือนมกราคมก็เด้งกลายเป็น 2,000 บาทไปด้วย (หรือถ้าลบบริการทิ้ง ยอดขายเก่าก็หายไปเลย!) แถมเดิมใช้วันที่ลูกค้าแจ้งซ่อม (`created_at`) แทนวันที่ซ่อมเสร็จจริง
- **วิธีแก้ไขที่ทำแล้ว:**
  - เพิ่มคอลัมน์ `final_price` (ราคาสุทธิที่ล็อกไว้ตอนปิดงาน) และ `completed_at` (วันและเวลาที่ซ่อมเสร็จจริง) ในตาราง `inbox_messages` (`backend/src/db/schema.ts`)
  - แก้ `backend/src/controllers/inbox.controller.ts` เมื่อกดปิดงานเป็น `completed` ให้คัดลอกราคาบริการ ณ ตอนนั้นมาล็อกเก็บไว้ใน `final_price` และประทับเวลา `completed_at` ทันที (และถ้าเปลี่ยนกลับเป็น `pending` ก็จะล้างค่าออก)
  - แก้ `backend/src/controllers/dashboard.controller.ts` ให้คำนวณรายรับรวม, รายสัปดาห์ (7 วัน), และรายเดือน (30 วัน) จาก `final_price` และ `completed_at` ต่อให้ในอนาคตแอดมินแก้ราคาหรือลบบริการทิ้ง ยอดเงินย้อนหลังก็จะไม่เพี้ยนอีกต่อไป

### ข้อ 4: `ไม่มี rate limit ที่ /auth/login และ POST /inbox`
- **แปลภาษาง่ายๆ:**
  - `Rate Limit` คือ **"การจำกัดความถี่ในการกดรัวๆ"** (เช่น 1 คน ห้ามกดเกินกี่ครั้งภายในกี่นาที)
  - ถ้าไม่มีตัวกั้นนี้:
    1. ที่หน้า `/auth/login`: แฮกเกอร์สามารถใช้โปรแกรมสุ่มรหัสผ่านรัวๆ วินาทีละเป็นพันครั้ง (Brute-force) จนกว่าจะเดาถูก
    2. ที่หน้า `POST /inbox` (ฟอร์มแจ้งซ่อมหน้าเว็บ): คนไม่หวังดีสามารถเขียนบอทยิงข้อความขยะ (Spam) เข้ามาเป็นหมื่นรายการในนาทีเดียวจนระบบล่มได้
- **วิธีแก้ไขที่ทำแล้ว:**
  - สร้างไฟล์ `backend/src/middlewares/rateLimit.middleware.ts` จำกัดให้ล็อกอิน (`POST /api/auth/login`) และส่งฟอร์มแจ้งซ่อม (`POST /api/inbox`) ได้ไม่เกิน **10 ครั้ง ต่อ 15 นาที ต่อ 1 IP** หากกดรัวเกินกำหนด ระบบจะตอบกลับสถานะ `429 Too Many Requests` ให้รอสักครู่ค่อยลองใหม่

### ข้อ 5: `seed เป็น Admin/1234 และอยู่ใน README → อ่านจาก env`
- **แปลภาษาง่ายๆ:**
  - ไฟล์สร้างข้อมูลเริ่มต้น (`backend/src/db/seed.ts`) และคู่มือ `README.md` เดิมเขียนรหัสผ่านแอดมินตายตัวไว้ว่า `Admin` / `1234`
  - ถ้าเอาขึ้นเซิร์ฟเวอร์จริงแล้วใครมาอ่านโค้ดบน GitHub เขาก็เอา `Admin` / `1234` มาล็อกอินเข้าหลังบ้านเว็บจริงของเราได้เลย
- **วิธีแก้ไขที่ทำแล้ว:**
  - แก้ `backend/src/db/seed.ts` ให้อ่านชื่อผู้ใช้และรหัสผ่านเริ่มต้นจากไฟล์ `.env` แทน (`SEED_ADMIN_USERNAME`, `SEED_ADMIN_PASSWORD`, `SEED_TECH_USERNAME`, `SEED_TECH_PASSWORD`) และไม่พิมพ์รหัสผ่านจริงออกทางหน้าจอ Console หรือใน `README.md`

### ข้อ 6: `ช่างลบ ticket ได้ → ให้ลบได้เฉพาะ admin และช่างแก้ได้เฉพาะงานของตัวเอง`
- **แปลภาษาง่ายๆ:**
  - เดิมที:
    1. ช่างซ่อมสามารถกดลบใบแจ้งซ่อมของลูกค้าทิ้งได้ (`DELETE /api/inbox/:id` เดิมใช้ `requireStaff`) ซึ่งในงานจริงช่างไม่ควรลบใบงานทิ้งเองได้
    2. เวลาอัปเดตสถานะงานซ่อม (`PATCH /api/inbox/:id/status`) เดิมช่างคนไหนก็กดเข้าไปแก้สถานะหรือแย่งงานที่มอบหมายให้ช่างคนอื่นไปแล้วได้
- **วิธีแก้ไขที่ทำแล้ว:**
  - ใน `backend/src/routes/inbox.routes.ts`: เปลี่ยนสิทธิ์ `DELETE /api/inbox/:id` จาก `requireStaff` เป็น **`requireAdmin` (ลบได้เฉพาะ Admin เท่านั้น)**
  - ใน `backend/src/controllers/inbox.controller.ts`: ดักเช็กว่าถ้าผู้ใช้งานเป็นช่าง (`technician`) จะสามารถแก้ไขได้เฉพาะ **"งานของตัวเอง (`technician_id === req.user.u_id`)"** หรือ **"งานที่ยังไม่มีผู้รับผิดชอบ (`technician_id === null`)"** เท่านั้น หากพยายามแก้ใบงานของช่างคนอื่น ระบบจะบล็อกด้วย `403 Forbidden`
  - ในหน้าเว็บ `frontend/src/pages/Admin/AdminInbox.tsx`: ซ่อนปุ่มลบเมื่อล็อกอินเป็นช่าง และล็อกฟอร์มไม่ให้ช่างแก้ไขงานของช่างคนอื่น

### ข้อ 7: `JWT อายุ 7 วันเก็บ role ไว้ ถ้าไม่เช็ก DB ซ้ำ ลบ/เปลี่ยน role แล้ว token เก่ายังใช้ได้`
- **แปลภาษาง่ายๆ:**
  - เวลาล็อกอิน ระบบจะออกบัตรผ่าน (Cookie JWT Token) ที่มีอายุอยู่ได้นาน **7 วัน** โดยในบัตรจะปั๊มตำแหน่ง (`role`) เอาไว้
  - ปัญหาคือ: สมมติวันนี้ช่างลาออก แอดมินเลยกด **ลบบัญชีช่างคนนั้นทิ้ง** หรือ **เปลี่ยนตำแหน่ง** ในฐานข้อมูล แต่ในคอมพิวเตอร์ของช่างคนนั้นยังมีบัตรผ่านที่ยังไม่ครบ 7 วันค้างอยู่!
  - ถ้ายามเฝ้าประตู (`auth.middleware.ts`) ดูแค่ว่าบัตรยังไม่หมดอายุโดยไม่เช็กฐานข้อมูลซ้ำ คนที่โดนลบชื่อไปแล้วจะยังเข้าใช้งานระบบต่อได้อีกตั้ง 7 วัน
- **วิธีแก้ไขที่ทำแล้ว:**
  - แก้ `backend/src/middlewares/auth.middleware.ts` ให้เมื่อตรวจบัตรผ่านเสร็จ จะนำ `u_id` ไปเช็กกับตาราง `users` ในฐานข้อมูลสดๆ ทุกครั้ง:
    1. ถ้าไม่พบชื่อในฐานข้อมูลแล้ว (ถูกลบไปแล้ว) ระบบจะสั่งล้าง Cookie และเตะออกทันที (`401 Unauthorized`)
    2. ดึงค่า `role` ล่าสุดจากฐานข้อมูลเสมอ ทำให้ถ้าแอดมินเปลี่ยนตำแหน่ง สิทธิ์ใหม่จะมีผลทันทีในวินาทีนั้นเลย

## 🗄️ 3. รายการแก้ไขส่วนฐานข้อมูล (Database) 4 ข้อ

### 3.1 `role` และ `repair_status` ควรเป็น Enum
- **แปลภาษาง่ายๆ:** เดิมคอลัมน์ `role` และ `repair_status` ตั้งเป็น `varchar(20)` คือช่องใส่ข้อความอะไรก็ได้ ถ้าเขียนโค้ดผิดเผลอส่งคำอื่นลงไป ฐานข้อมูลก็ยอมรับ
- **วิธีแก้ไขที่ทำแล้ว:** เปลี่ยนเป็น `pgEnum` ใน PostgreSQL (`user_role`: `'admin' | 'technician'` และ `repair_status`: `'pending' | 'completed'`) เพื่อล็อกระดับฐานข้อมูลให้รับได้เฉพาะค่าที่กำหนดไว้เท่านั้น

### 3.2 ไม่มี Index บนคอลัมน์ที่ใช้ Filter
- **แปลภาษาง่ายๆ:** `Index (ดัชนี)` เปรียบเหมือน **"สารบัญหนังสือ"** ถ้าไม่มีสารบัญ เวลาค้นหาหรือกรองงานซ่อม ฐานข้อมูลต้องไล่เปิดอ่านทีละแถวตั้งแต่ต้นจนจบ ยิ่งข้อมูลเยอะเว็บยิ่งช้า
- **วิธีแก้ไขที่ทำแล้ว:** เพิ่ม Index ให้กับคอลัมน์ที่ใช้กรองทั้งหมดใน `backend/src/db/schema.ts` ได้แก่:
  - `idx_services_cg_id`, `idx_services_status`
  - `idx_users_role`
  - `idx_inbox_service_id`, `idx_inbox_technician_id`, `idx_inbox_repair_status`, `idx_inbox_is_read`, `idx_inbox_created_at`

### 3.3 ลบ Category แล้ว Cascade ลบ Services ทิ้งหมด
- **แปลภาษาง่ายๆ:** เดิมตั้งค่า `onDelete: 'cascade'` ที่ตาราง `services.cg_id` แปลว่าถ้าแอดมินเผลอลบหมวดหมู่ `"Computer"` บริการซ่อมคอมพิวเตอร์ทั้งหมดในหมวดนั้นจะถูกลบทิ้งหายเกลี้ยงตามไปด้วยทันที!
- **วิธีแก้ไขที่ทำแล้ว:** เปลี่ยนเป็น `onDelete: 'restrict'` แปลว่าถ้าหมวดหมู่นั้นยังมีบริการผูกอยู่ ฐานข้อมูลจะไม่อนุญาตให้ลบหมวดหมู่นั้น เพื่อป้องกันข้อมูลบริการหายโดยไม่ตั้งใจ

- **แปลภาษาง่ายๆ:** ใน `README.md` เดิมเขียนอธิบายโครงสร้างตารางและสิทธิ์ API บางจุดไม่ตรงกับโค้ดจริง

## 🔍 4. จุดเล็กๆ น้อยๆ (Minor Points) 3 ข้อ

### 4.1 `GET /inbox/:id มี side effect (ควรเป็น PATCH)`
- **แปลภาษาง่ายๆ:** ตามมาตรฐานการออกแบบ API คำสั่ง `GET` มีไว้สำหรับ **"ขอดูข้อมูลอย่างเดียว"** ไม่ควรแอบไปแก้ไขข้อมูลในฐานข้อมูล (การที่คำสั่ง `GET` แอบไปแก้ฐานข้อมูลให้ `is_read = true` เรียกว่ามี *Side Effect* หรือผลข้างเคียงแฝง)
- **วิธีแก้ไขที่ทำแล้ว:**
  - แก้ `GET /api/inbox/:id` ให้ดึงข้อมูลอย่างเดียวโดยไม่แอบแก้ฐานข้อมูล
  - สร้าง Endpoint ใหม่ `PATCH /api/inbox/:id/read` สำหรับเปลี่ยนสถานะเป็น *"อ่านแล้ว (`is_read = true`)"* โดยเฉพาะ และให้หน้าเว็บ `AdminInbox.tsx` เรียกใช้ `PATCH` เมื่อเปิดอ่านข้อความ

### 4.2 `mount route ซ้ำ / กับ /api เพื่อแก้ Vercel`
- **แปลภาษาง่ายๆ:** ในไฟล์ `backend/src/index.ts` เดิมมีการเขียน `app.use('/api', apiRoutes)` และ `app.use('/', apiRoutes)` ซ้ำกัน 2 บรรทัด
- **วิธีแก้ไขที่ทำแล้ว:** ลบการ mount ซ้ำที่ `'/'` ออก เหลือเพียง `app.use('/api', apiRoutes)` และ `app.get('/api/health', healthCheck)` ให้สะอาดและตรงตามมาตรฐาน

### 4.3 `รูปแนบเป็นแค่ URL (รับได้สำหรับ STARTER)`
- **แปลภาษาง่ายๆ:** ระบบแนบรูปตอนนี้ใช้วิธีวางลิงก์ URL ของรูปภาพแทนการอัปโหลดไฟล์จริง ซึ่งผู้ตรวจระบุว่า **"ยอมรับได้สำหรับโปรเจกต์ระดับเริ่มต้น (Starter)"** ไม่จำเป็นต้องแก้ในขั้นตอนนี้ครับ

## 📂 5. สรุปรายชื่อไฟล์ทั้งหมดที่ได้รับการอัปเดต

1. `backend/src/config/env.ts` *(สร้างใหม่ — ตรวจสอบ `JWT_SECRET` และตั้งค่า CORS Whitelist)*
2. `backend/src/middlewares/rateLimit.middleware.ts` *(สร้างใหม่ — จำกัดความถี่การยิง API หน้า Login และฟอร์มแจ้งซ่อม)*
3. `backend/src/middlewares/auth.middleware.ts` *(เช็กสถานะผู้ใช้และ Role ล่าสุดจากฐานข้อมูลจริงทุกครั้ง)*
4. `backend/src/db/schema.ts` *(เพิ่ม PostgreSQL Enums, Indexes, `final_price`, `completed_at`, และ `onDelete: 'restrict'`)*
5. `backend/drizzle/0002_feedback_improvements.sql` *(ไฟล์ SQL Migration และรันอัปเดตบนฐานข้อมูล Neon จริงเรียบร้อยแล้ว)*
6. `backend/src/db/seed.ts` & `backend/.env.example` *(เปลี่ยนให้อ่านรหัสผ่านเริ่มต้นจาก `.env`)*
7. `backend/src/index.ts` *(ตั้งค่า CORS Whitelist และลบ Route ที่ mount ซ้ำ)*
8. `backend/src/routes/auth.routes.ts` & `backend/src/routes/inbox.routes.ts` *(เพิ่ม Rate Limit, เพิ่ม `PATCH /api/inbox/:id/read`, และจำกัดการลบเฉพาะ Admin)*
9. `backend/src/controllers/auth.controller.ts`, `backend/src/controllers/inbox.controller.ts`, `backend/src/controllers/dashboard.controller.ts` *(อัปเดต Logic ทั้งหมดตาม Feedback)*
10. `frontend/src/types/index.ts` & `frontend/src/pages/Admin/AdminInbox.tsx` *(รองรับ `PATCH /read`, ซ่อนปุ่มลบสำหรับช่าง, และล็อกไม่ให้ช่างแก้งานของคนอื่น)*
11. `README.md` *(อัปเดตเอกสารให้ตรงกับ Schema และระบบความปลอดภัยใหม่ทั้งหมด)*
